# NRF51822 最新交接与 J-Link 烧录

## 目标

检查新收到的 NRF51822 墨水屏交接资料，确定应烧录的固件，并通过 J-Link 下载到目标板后进行最小验证。

## 结论

- 新压缩包是此前交接资料的重复副本，109 个资料文件与旧交接源码一致；旧目录多出的 11 个文件只是本地晶振测试构建产物。
- 未直接执行交接包中的脚本或程序。包内 DFU 私钥仅留在本机资料区，不记录、不提交、不上传。
- 继续使用基于交接源码整理完成的 InkDesk v1.0.0 产品固件，而不是退回原始 BLE 传图示例。
- J-Link App-only 烧录成功，保留了现有 S130 和 Secure Bootloader。
- 应用回读 24,524 字节与本次构建 BIN 的 SHA-256 完全一致；v6 settings 的版本、长度和有效 App 标记正确。
- Bootloader 可以跳转到应用，`sd_ble_gap_adv_start()` 返回 `0`。但 Windows 多轮扫描仍未发现 `EPD_Ink` 或 Nordic UART Service UUID，所以 BLE 空口不能标记为通过。

## 再次检查（11:34）

- J-Link 再次识别 NRF51822 XXAC，VTref 仍为 3.300 V。
- 从 `0x0001B000` 回读 24,524 字节，SHA-256 仍与构建 BIN 完全一致；v6 settings 未变化。
- 应用运行状态为 `DEV_REFRESHING`、`display_busy=1`、`last_error=0`；P0.15/BUSY 为高，说明开机显示任务正在等待屏幕控制器，不是应用未启动。
- 连接句柄持续为 `0xFFFF`，证明设备没有被其他 BLE 主机占用。
- RADIO 高速采样捕获到活动状态，HFCLK 在活动期切到外部 16 MHz 晶振源；频率寄存器覆盖 2、26、80 MHz 偏移，对应 BLE 的三个广播信道，且出现有效 PacketPtr。
- Windows 再次独立扫描 20 秒，仍未发现 `EPD_Ink`。因此软件已推进到实际广播事件，但天线后的空口可见性或 Windows 接收侧仍未闭环。

## 历史连接证据与纠正

- 交接包原始压力测试日志证明，同一项目的原始 `epd_ble_xfer` 固件曾在 2026-08-09 扫描、连接并持续运行 2 小时。
- 测试期间完成 710/710 次 PING、0 次重连、0 个错误，并完成 1 次 TIME 刷新和 3 次 CLOCK 刷新。
- 因此“板上 BLE/天线从未验证”是不准确的。当前故障应按“旧固件可连、当前产品固件不可见”的回归问题处理，同时保留供电或硬件状态后来变化的可能。
- 旧稳定固件使用外部 32.768 kHz X2 作为 SoftDevice LFCLK；当前产品固件改为 RC LFCLK（`rc_ctiv=16`、`rc_temp_ctiv=2`）。设备名、广播间隔和广播启动流程没有关键差异。
- 下一步优先把当前产品固件 LFCLK 恢复为外部 X2 后重建、App-only 烧录和扫描；若恢复后仍不可见，再用原始已验证 App 做 A/B 烧录，最后才把重点转向天线和主机。

## 可复用方法

1. 对重新发送的交接包先做哈希清单与逐文件比较，避免把附件编号误当成软件版本。
2. 板上已有匹配的 SoftDevice 和 Bootloader 时，优先写应用与匹配 settings，避免无必要的整片擦除。
3. 烧录后从实际应用起始地址按 settings 中的应用长度回读，并与构建 BIN 做哈希比较。
4. 分开记录三层证据：写入/回读一致、应用运行到广播调用、主机实际扫描并完成协议查询。
5. J-Link Commander 的 `savebin` 长度参数应显式写成 `0x...`，避免裸数字按十六进制解释造成过量回读。

## 待处理

- 用手机或另一只 BLE 适配器交叉扫描 `EPD_Ink`。若另一主机可见，处理 Windows 蓝牙适配器/缓存；若所有主机都不可见，优先检查天线、匹配网络、焊接与射频路径。
- 显示侧 P0.15/BUSY 持续为高；确认 U13/屏幕刷新侧 5 V、FPC 和 SSD1683 供电后再判断显示故障。
- 广播可见后执行 `PING → INFO → CAPS → STATUS`。
- 确认显示侧 5 V 后，再做三色测试图和完整传图；屏幕未目视通过前不宣称整机验收完成。

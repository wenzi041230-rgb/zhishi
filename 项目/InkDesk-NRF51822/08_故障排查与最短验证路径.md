# 故障排查与最短验证路径

## 最短实板验证

1. J-Link 读取芯片，确认目标为 NRF51822 XXAC、电压约 3.3 V。
2. 烧录 App-only 包和匹配 settings，复位运行。
3. 8 秒扫描 `EPD_Ink`。
4. 连接并订阅 NUS TX。
5. 依次查询：`PING`、`INFO`、`CAPS`、`STATUS`。
6. 同步时间，等待 `TIME_OK` 和 `CLK_OK`。
7. 确认屏幕有 5 V，执行 `TEST bands`。
8. 发送 BW/RED 图片，等待两个 `DATA_OK` 和最终 `SHOW_OK`。

## 症状矩阵

| 症状 | 优先检查 | 不要过早下的结论 |
|---|---|---|
| J-Link 连不上 | SWDIO、SWCLK、GND、VTref、芯片型号和速度 | 不一定是固件损坏 |
| 有 3.3 V、无广播 | App/SoftDevice/settings 是否成套、复位、X1、天线 | 编译成功不代表 BLE 已运行 |
| 能连接但不刷新 | 5 V/U13、FPC、RST、BUSY、屏幕型号 | BLE 正常不代表显示供电正常 |
| `BUSY` | 是否仍在刷新或已有 Job | 不要重复发送并覆盖状态 |
| `NO_BW` | 是否收到 BW 的 `DATA_OK` | RED 不能代替 BW |
| 图片错位或缺块 | 数据是否恰好 15,000 字节、方向、bit 顺序 | 不一定是屏幕坏了 |
| `TIME_ERR` | 月份、日期和 HH/MM/SS 范围 | 固件不会静默修正非法时间 |
| Windows 找不到服务 | GATT 缓存、旧配对、蓝牙重启 | 不一定需要重新烧录 |
| OTA 中断 | 距离、RSSI、供电、是否仍广播 DfuTarg | 正常断连是进入 DFU 的一部分 |

## 晶振诊断知识

- X1 影响高频系统和射频；X2 影响外部低频时钟。
- 当前专用测试结果为 X1、X2 均能起振。
- 正式固件仍用 RC LFCLK，所以判断 32 kHz 是否起振必须用专用测试或寄存器证据，不能只看 App 走时。
- 临时诊断固件测试后必须恢复 SoftDevice、App、Bootloader 和 settings。

## 广播启动成功但主机扫描不到

把软件调用证据和无线空口证据分开：

1. 在 `sd_ble_gap_adv_start()` 返回后设置一次性断点；返回码 `0` 只证明 SoftDevice 接受了广播请求。
2. 确认 Bootloader 能跳入 `0x0001B000` 应用区，程序计数器进入应用代码。
3. 主机仍扫描不到时，继续检查 HFCLK/X1、射频匹配与天线、主机蓝牙缓存/适配器、供电和周边干扰。
4. 墨水屏 BUSY 长等待不应被误判为程序未启动；当前固件在屏幕任务前已调用广播启动。
5. 只有扫描到 `EPD_Ink` 并完成 `PING/INFO/CAPS/STATUS`，才能把 BLE 运行链路标为通过。

更强的软件侧证据可以继续读取 RADIO：未连接句柄应为 `0xFFFF`；广播期间 RADIO 状态应变化，HFCLK 应切到外部高频晶振，频率寄存器应覆盖 2、26、80 MHz 偏移。满足这些条件仍扫不到时，问题优先级从“固件未启动”转向天线/匹配网络/焊接/接收主机，但这些寄存器仍不能代替真正的空口抓包。

2026-08-15 现场状态：产品版和交接版的应用区回读均一致；交接版烧录后广播启动返回 `0`，RADIO 在三个 BLE 广播信道活动，HFCLK 活动期切到外部 16 MHz 晶振，连接句柄为 `0xFFFF`。同一 Windows 主机多轮扫描仍未观测到 `EPD_Ink` 或 NUS UUID，因此天线后的空口可见性仍为待验证。

历史对照与 A/B 结果：2026-08-09 原始 App 使用外部 X2 LFCLK，曾完成 2 小时 BLE 压测，710 次 PING 全部成功且 0 次重连；2026-08-15 重新烧录同类交接版 X2 固件后仍不可见。因此 LFCLK 仍需保留为配置知识点，但不能再单独解释当前故障，排查应转向手机/第二适配器、天线与匹配网络、焊接、供电和主机接收侧。

## 成功边界

- `EPD_OK`：BLE NUS 命令链路正常。
- `DATA_OK`：一个平面完整收到，不代表已经刷新。
- `SHOW_OK`：SSD1683 刷新完成，是 App 标记成功的唯一依据。
- 屏幕肉眼正确：最终硬件验收；协议成功不能代替目视检查。
